# daily-post-2026-11 ― サジェストKWから「リライトか新規か」を決めて記事にするルール

作成: 2026-11-09（Claude Code）／対象: `suggest/bouon-{high,mid,low}/` のラッコキーワード（Bing サジェスト）

このフォルダのサジェストを、1クエリ（正確には「1つの意図のまとまり」）ずつ記事にするための運用ルール。
**判断の順番は「重複を探す → あればリライト → なければ新規」で固定する。**

タイトル・description・導入・H2 の作り方そのものは `bouon-writing` の `references/query-intent-match.md`（クエリ契約）が正本。本書はその前段（どのクエリを、どの記事で受けるか）と、サジェスト起点の記事に必要な要素を決める。両者が食い違う場合は query-intent-match.md を優先する。

---

## 0. 原則（6つ）

1. **1つの意図＝1つのURL。** 同じ答えで満たせるクエリを2つの記事で狙わない（カニバリで両方沈む）
2. **重複の疑いがあればリライトを優先する。** 既存URLは評価と被リンクを持っている。新規記事はゼロからのスタートになる
3. **リライトでも slug は変えない。** タイトルを変えるときは GSC で既存の流入クエリを確認し、それを失わない形にする
4. **サジェストは「需要がある」証拠であって「量」の証拠ではない。** 無料枠は検索数が null。量の判断は GSC の表示実績を優先する
5. **Bing のサジェストは Google の代理として使う。** 主戦場は Google（2026-10-16 決定）。メインKWを決めるときは Google のサジェスト／検索結果でも同じ語が出るかを確認する
6. **統合済みのテーマは新規記事を作らない。** 音大生×地域・地方4都市・在宅ワーク系など、メモリと `.task-management/records/` に「統合済み・復活しない」とあるテーマは、該当する統合記事へのリライトに回す

## 1. データの読み方

CSV は **UTF-16・タブ区切り**。読むときは変換する。

```bash
iconv -f UTF-16 -t UTF-8 "<file>.csv" | tr -d '"\r'
```

| 列 | 意味 | 使い方 |
|---|---|---|
| 区分 `＋` | シード語の直下のサジェスト（1段目） | **意図の幹。** メインKW候補はここから選ぶ |
| 区分 `＋＋` | 2段目（`＋`の語をさらに広げたもの） | サブKW・H2・FAQ の候補 |
| 区分 `＋α` | 関連の薄い派生（文字の一致だけのものが多い） | 基本は捨てる。防音Labの読者が打つ語だけ拾う |
| 単語数 | スペースで区切った語数 | 3語以上は具体的な悩み。FAQ の H3 にそのまま使いやすい |
| 検索数・CPC・競合性 | 無料枠は null | 使わない |

### 捨てる語（ノイズの除外）

次のどれかに当たる語は、記事の素材にしない。

- 防音・騒音と無関係（例: 「ハノイ pizza 4p's」「日本ハム nh-427」「l-ラムノース」）
- 他社のサービス名・ECサイト名で、指名検索として記事を書く価値がないもの（例: 「ノイズ対策.com」）
- 防音Labの読者（住まい・楽器・配信・睡眠の音の悩みを持つ人）がほぼ打たない専門分野（例: 「4-20mA ノイズ」「1/f ノイズ 評価」＝計測・電子工学）
- 地名だけ違う語の大量バリエーション（「防音 賃貸 埼玉」「〜千葉」…）は、1つずつ記事にしない。**1グループとして扱う**（§3-4）

## 2. 優先度の決め方

フォルダの high / mid / low は「どのシードから着手するか」の順番。シードの中では次の順に処理する。

| 順 | 条件 | 理由 |
|---|---|---|
| 1 | GSC で既に表示があるのに、タイトルにもH2にもその語がない | 最短で成果が出る（リライトで拾える） |
| 2 | `＋` の語で、`＋＋` の派生が多い（需要の幹） | 1記事で拾える語が多い |
| 3 | 費用・比較・効果確認型（お金が動く直前の検索） | 収益導線（CtaBox・アフィリエイト）につながる |
| 4 | 手順型・直接回答型 | AI Overview に答えを取られやすいので、確かめ方・例外を足せる語だけ |
| 5 | `＋α` から拾った語 | 最後。単独記事にせず FAQ で受けることが多い |

**1日の単位は「1つの意図のまとまり（＝1記事分）」。** 新規でもリライトでも1件と数える。

## 3. 手順（1シードあたり）

### 3-1. 素材を整える

1. CSV を変換し、§1 のノイズを除外する
2. 残った語を「検索者が欲しい答え」でグループに分ける（query-intent-match.md Step 0-2）。迷ったら2語で検索し、上位10件のURLが半分以上重なれば同じグループ
3. 各グループにクエリ型（直接回答／効果確認／費用／比較・選択／手順／探索）を付ける

### 3-2. 重複を探す（必須・3段階）

グループごとに、次の3つを**すべて**行う。1つでも当たれば「重複の疑いあり」。

| 段階 | 方法 | 当たりの基準 |
|---|---|---|
| A. 記事一覧 | `.workspace/.data-set/interlink-postlist.md` を、グループの主要語とその言い換え（遮音／防音、内窓／二重窓、ハムノイズ／アースノイズ など）で Grep | タイトルかタグに主要語がある |
| B. 本文 | `src/content/ja/` を Grep（H2・H3 に主要語があるか） | 主要語を含む H2 がある |
| C. 検索実績 | GSC 画面で主要語の部分一致クエリ → どのページが表示されているか | 自サイトのページが表示されている（順位は問わない） |

再生成が古い場合に備え、A の前に `node .workspace/scripts/build-interlink-postlist.mjs` を実行してよい。

### 3-3. リライトか新規かを決める（判定表）

上から順に当てはめ、最初に当たった行で決める。

| # | 状況 | 判定 | やること |
|---|---|---|---|
| 1 | 統合済みテーマ（原則6）に当たる | **リライト**（統合記事へ） | 統合記事に H2/FAQ を足す |
| 2 | 既存記事のメインKWがグループのメインKWと同じ | **リライト** | クエリ契約を書き直し、足りない H2・FAQ を足す |
| 3 | 既存記事が同じ答えを返しているが、タイトルにクエリの語がない（意図は合っている、語がずれている） | **リライト（タイトル修正あり）** | 段階Cで流入クエリを確認し、失うものがなければタイトルとH2に語を入れる |
| 4 | 既存記事が10位以内でCTR 3%以上 | **リライト（タイトル据え置き）** | タイトル・descriptionは触らず、H2/FAQ の追加だけ |
| 5 | 既存記事の1つのH2として扱われているが、グループの `＋＋` が5語以上あり、欲しい答えが既存記事の主題と違う | **新規**（既存記事と役割分担） | 既存記事の該当H2は要約にし、新記事へ内部リンク。新記事から既存記事へも戻す |
| 6 | 既存記事の1つのH2として扱われていて、グループが小さい（`＋＋` 4語以下） | **リライト** | 既存のH2を厚くするか、FAQに足す |
| 7 | 既存記事は同じ語を含むが、答えている質問が違う（例: 「遮音シート 重さ」でブースの補強を書いた記事 vs 「遮音シート 効果」） | **新規** | 新記事を作り、既存記事と相互リンク。既存記事のタイトルが新記事のメインKWを含む場合は、既存側を語の重ならないタイトルへ寄せる |
| 8 | 既存記事が21位以下に沈んでいて、構成からクエリとずれている | **作り直し**（slug維持のリライト） | `bouon-rewrite-strategy` に従い構成から再設計。新規URLは作らない |
| 9 | 3-2 のどれにも当たらない | **新規** | §4 の要素で作成 |

**迷ったらリライトを選ぶ。** ただし「既存記事に全然違う主題のH2を足して1記事に何でも入れる」ことはしない（記事の主題がぼやけて、元のクエリの順位も落ちる）。その場合は #5・#7 で新規にする。

### 3-4. 地名・属性バリエーションの扱い

「防音 賃貸 東京／大阪／埼玉」「〜7万」「〜安い」のように、同じ質問に条件を付けた語は、

- 原則は**1つの記事の中で受ける**（地域別・予算別の H2 か表）
- 単独記事にしてよいのは、①GSC で表示30回以上（3か月）、②その条件でしか答えられない一次情報（物件の探し先・相場）が書ける、の両方を満たすときだけ
- 都市別の記事は統合済み（原則6）。復活させない

### 3-5. 記録する

判定はシードごとの台帳 `triage/<シード>.md` に残す（§7 のひな形）。起票は `.task-management/` のルールに従う。Codex に渡す場合は `hq/org/work-order-template.md` で指示書を書く。

### 3-6. アウトラインと体験チェッカー（Claude の段階）

新規・リライトとも、完成稿に入る前に **Claude がアウトラインを作り、ユーザー（筆者・さしし）に体験チェッカーで質問する**。ユーザーの答えで、言葉の分かりやすさと「読者が想像できるか・体験できるか」を最終調整してから完成稿に渡す。この段階は Claude が受け持つ（Codex に渡さない）。

1. Claude がアウトラインを `_draft/<slug>-outline.md` に作る。中身は「クエリ設計」（query-intent-match.md Step 0-6）＋見出し構成＋図解計画＋体験の型（§4-4 ④）＋導入3文の試し書き
2. 同じファイルの末尾に、§8 の体験チェッカーから質問を選んで書く（1記事6〜10問）
3. ユーザーが callout で答える（§8-1 の書式）
4. Claude が答えをアウトラインに反映し、「体験チェックの反映」節に何を変えたかを書く
5. 反映済みのアウトラインを材料にして、完成稿を作る（§3-7）。指示書の「材料」にアウトラインのパスを書く
6. 記事を公開したら、回答のうち筆者の体験（§8 の C）と書き方の好み（H や言い回しの指摘）を `.workspace/.data-set/author-experience.md` に追記し、アウトラインは削除する（2026-11-14 ユーザー指示。次の記事では体験をまずこのファイルから探す）

答えが空のまま3日たった質問は、その項目を「確認なし」として進めてよい。ただし体験の質問（§8 の C）が空なら、筆者の体験は書かない。

### 3-7. 完成稿の作成とモデルの選び方

完成稿はユーザーがその日のリソース（使用量・時間）を見て、作り手を選ぶ。指定がなければ下の既定で作る。

| 作り手 | 既定のモデル | 呼び方 |
|---|---|---|
| Codex（標準） | 既定モデル（2026-11-14 時点 gpt-6.1-sol）・推論 medium | `node $CODEX task --write --effort medium --cwd C:/Users/sasis/344blog/bouon-lab --prompt-file .workspace/codex/orders/<指示書>.md`（`$CODEX` の場所は `hq/org/README.md` §3） |
| Claude Code | Sonnet 5.5（`claude-sonnet-5-5`） | サブエージェントで書く場合は model に `sonnet` を指定する |

- 使ったモデルと推論の強さを、台帳の「状態」欄と Codex の報告書に書く（モデルごとの仕上がりを比べるため）
- Sonnet 5.5 は T-60（2026-11-10）で5本とも公開できる仕上がりだったため、Claude Code 側の既定として確定した（[結果](2026-11-10-model-test.md#結論2026-11-10ユーザー判定のあと)）。窓口・制度・機関の名称は検収で一次情報と照らす
- gpt-5.5 は ChatGPT アカウントの Codex では使えない（2026-11-14 エラー）。`--model` を付けず `~/.codex/config.toml` の既定（gpt-6.1-sol）で書く。T-65（2026-11-14）で4本とも合格・文字数も上限内だった（ユーザー承認 2026-11-14）
- 指示書には文字数の上限、dB の体感を独自に書かないこと、日本語の一次資料を優先することを書く（T-60 で5本に共通した傾向）

## 4. 新規記事に入れる要素

クエリ契約（query-intent-match.md Step 1）を書いてから、次の要素を揃える。

### 4-1. 必須要素（すべての記事）

| 要素 | 中身 | SEO上の理由 | コピー上の理由 |
|---|---|---|---|
| **クエリ設計ブロック** | メインKW1つ・サブKW2〜5個・クエリ型・欲しい答え・検索結果で完結しない理由・カニバリ確認（どの既存slugと役割分担したか） | 1記事1意図を守る | 書く前に「誰の何に答えるか」を固定する |
| **タイトル** | メインKWをそのままの語順で先頭15字以内＋疑問か結論の半分＋検索結果にない判断材料。28〜38字 | タイトルは関連性の最も強い手がかり | 検索結果で「自分の語」と「開く理由」を同時に見せる |
| **description** | 前半60字にメインKWと結論、後半に記事の中身（表・チェックリスト・試算）と対象者。80〜120字 | 一致語が太字になる | 開いた先に何があるかを約束する |
| **導入（最初の3文）** | ①メインKWを含む結論 ②調べて分かったこと（根拠の出どころ） ③この記事で分かる確かめ方・例外の予告 | 着地直後の離脱を防ぐ | 答えより先に共感や問いかけを置かない |
| **最初のH2** | メインKWを入れ、そこでメインKWに直接答える | 主題の明示 | 目次を見た人が最短で答えに着く |
| **サブKW対応のH2** | サブKWごとにH2かFAQのH3を1つ。どこにも入らないサブKWは契約から外す | 拾える語を増やす | 読者の次の疑問の順に並べる |
| **判断材料** | 比較表・数値の幅・チェックリスト・「自分の場合」の当てはめ方のどれか1つ以上 | AI Overview や検索結果で完結しない価値 | クリックする理由そのもの |
| **限界・効かない場合** | 「ここまでは効く／ここからは効かない」の境界 | 効果確認型の上位条件 | 誇大を避け、信頼を得る（Persona Ω） |
| **FAQ** | `＋＋`・3語以上の疑問形サジェストを、語をほぼそのまま H3 に（3〜6問） | ロングテールを拾う | 読者が実際に打った言葉で答える |
| **内部リンク** | ①上位のハブ記事へ1本 ②同じクラスタの兄弟記事へ1〜2本 ③重複判定で役割分担した既存記事と相互リンク。文言はリンク先のメインKWを含める | クロールと評価の受け渡し | 次に読むものを迷わせない |
| **事実の裏取り** | 価格・製品仕様・制度・企業名は `bouon-research` に従い一次情報で確認 | 鮮度と正確さ | 間違い1つで記事全体が信用されなくなる |

### 4-2. クエリ型ごとに足す要素

| 型 | シードの例 | 足す要素 | 目安の文量 |
|---|---|---|---|
| 直接回答型 | 遮音シートとは／吸音材 防音材 違い | 冒頭1文の答え＋図解かメモ画像＋「自分の場合」の確かめ方。答えだけで終わらせない | 2,500〜4,000字 |
| 効果確認型 | 内窓 防音効果／防音カーテン 効果 | 効く音・効かない音の表、数値（dB・等級）は出典付き、「効果なし」と感じる原因 | 3,000〜5,000字 |
| 費用型 | 防音 リフォーム 費用／防音室 価格 | 裏取り済みの金額の幅、幅が出る条件、見積もりで見るところ、補助金の有無。数値はタイトル・description・本文で一致 | 4,000〜6,000字 |
| 比較・選択型 | 吸音材 おすすめ／内窓 防音 ランキング | 比較軸の明示、候補の表、「この条件ならこれ」の選び方。CtaBox は価格帯が合う商品だけ | 4,000〜7,000字 |
| 手順型 | 遮音シート 壁 貼り方／ハムノイズ 除去方法 | 原因の切り分け→手順→材料・道具・時間・費用。失敗例（賃貸の原状回復など） | 3,000〜5,000字 |
| 探索型 | 防音 賃貸 探し方 | 具体的な探し先（サイト名・検索条件）、内見チェックリスト、地域差の表 | 3,000〜5,000字 |

文量は上限ではなく目安。**文字数のために書き足さない**（比較・数値・事例で厚くする）。

### 4-3. 状況に応じて足す要素

- **メモ画像**: 表が2つ以上、または判断フローがある記事（`bouon-memo-image`）
- **本音と建前**: クエリ契約が決まった後に、本音フックを1か所（`bouon-persona-thinking`。テンプレ化しない）
- **収益導線**: 費用型・比較型は `bouon-growth-ops` で QUEST/PASONA/BEAF を選ぶ。CtaBox はメモリの使用ルールどおり、価格帯が合い商品名に触れた節だけ
- **筆者の体験**: 筆者本人が記録したものだけ使う。AI が体験を作らない
- **ハブカード**: 公開後、入口カードに載せるかを `bouon-hub-cards` で判断する

### 4-4. 知識を期待する読者への書き方：数字 → 文字で想像できる描写 → 図解 → 読者の体験（2026-11-09〜）

想定クエリからの流入実績を見ると、読者は**知識**（仕組み・数値・効く理由）を期待して来ている。そこで記事は次の4段で組む。

```
① 数字をハッキリさせる → ② 文字だけで場面と仕組みが思い浮かぶように書く → ③ 図解で1枚にまとめる → ④ 読者が自分の部屋に当てはめて「体験」する
```

文字の段階（②）で想像できない内容は、図解にしても伝わらない。図解は本文の代わりではなく、本文で言葉にした内容を1枚で確かめるものとする。

#### ① 数字をハッキリさせる

| ルール | 書き方 | NG |
|---|---|---|
| **4点セット** | 数値は「値・単位・条件・出典」をそろえる。例: 面密度 2.2kg/m²（厚さ1.2mm品・メーカー公表値） | 「重い遮音シート」「高性能」 |
| **ぼかし語を数値に置き換える** | 「かなり」「大幅に」「しっかり」「効果的」は、何が・どれだけ・どの条件で、に書き換える | 「防音効果が大幅にアップ」 |
| **幅には条件を付ける** | 幅で書くときは、幅が出る理由（広さ・構造・音の高さ）を同じ文か次の文に書く | 「費用は10〜100万円」だけ |
| **同じ物差しで比べる** | 比較表は同じ条件の数値だけを並べる。公表値と実測値、Dr値とD値、透過損失と体感は列を分けるか、別の表にする | 物差しの違う値を1列に並べる |
| **計算は式を見せる** | 試算・換算は式と前提を本文に書き、検算する（例: 6畳の壁1面 2.5m×3.6m＝9m²） | 結果の数字だけ書く |
| **用語は初出で定義する** | Dr値・透過損失・面密度・L値などは、初めて出る文で「何を測った数字か」を1文で説明する | 説明なしで単位だけ出す |
| **鮮度を書く** | 価格・制度・製品仕様は確認した年月を書く（「2026年11月に公式サイトで確認」） | 時期の分からない価格 |
| **分からない数値は埋めない** | 公表値がなければ「公表なし」と書く。推測や一般論で数字を作らない | もっともらしい概数 |
| **体感の言い換えは決まった表だけ** | dB の体感は `.workspace/.data-set/db-familiar-sound-scale.md` の言い方だけ使う（`bouon-writing` の規定どおり） | 記事ごとに例えを作る |

タイトル・description・導入・本文・図解の数値は完全に一致させる。

#### ② 文字だけで想像できるように書く

- **場面 → 仕組み → 数字の順に書く。** 「夜、隣の部屋のテレビの声が壁越しに聞こえる」（場面）→「声は壁のすき間と、壁そのものが揺れることで伝わる」（仕組み）→「壁の重さが2倍になると、遮る量は約○dB増える（出典）」（数字）
- **位置・向き・大きさを具体的な言葉で書く。** 「壁の内側」ではなく「石膏ボードと柱のあいだ」。大きさは身近な単位に換算して添える（畳1枚＝約1.6m²、A4用紙、2Lペットボトルなど。換算は計算で出せるものだけ）
- **音の通り道を言葉でたどる。** 音源 → 空気 → 壁・床・すき間 → 隣の部屋、のどこで何が起きるかを順に書く。図解の下書きになる
- **手順は動作の単位で書く。** 「貼る」ではなく「端を5cm重ねて、継ぎ目にテープを貼る」
- **1段落に新しい概念は1つ。** スマホで読む前提（段落の改行ルールはメモリ「スマホ優先の段落改行」）

#### ③ 図解で1枚にまとめる

- **知識系・効果確認型・手順型の記事は、図解を1枚以上入れることを基本にする。** アウトラインの段階で「図解計画」（何を・どのH2の直後に・どの種類で）を書く
- 図解にするものの選び方

  | 内容 | 図解の種類 | 手段 |
  |---|---|---|
  | 音の伝わり方・構造（壁の断面、内窓の空気層） | 断面図・経路図 | SVG → PNG（`.workspace/codex/image-style.md` §5-2） |
  | 数値の大小・前後比較（dB・面密度・費用） | 棒グラフ・前後比較図 | SVG → PNG（同上） |
  | 選択肢の比較（素材・商品・依頼先） | 比較メモ・早見表 | `bouon-memo-image` |
  | 「自分はどれを選ぶか」 | 判断フロー | `bouon-memo-image` |
  | 作業・確認の順番 | チェックリスト・手順図 | `bouon-memo-image` |

- **分担（2026-11-09 決定）**: 文字・数値の入る図はコードで描き（SVG・HTML → PNG）、AI の画像生成は文字のないサムネイルと場面・実物の絵だけに使い、記事内の AI 画像は「ここぞ」の0〜1枚に絞る（`image-style.md` §4-2）。トーンはスクリプト側（`bouon-presets.json`）で固定し、記事のプロンプトには写すものだけを書く。完成稿の作り手（Codex）は図解マーカー（`image-style.md` §5-2 の書式）を置き、Claude が検収で数値を確かめてから描く

- 図解は説明したH2の直後、本文の該当段落のすぐ後ろに置く
- 図解の数値は本文と一致させ、出典は本文側に書く（画像には「出典は本文参照」）
- 画像が見えなくても内容が分かるよう、alt に図の中身（何と何をどう比べたか）を書く
- 表が多い記事は、数値比較を画像にして本文の表を省いてよい（メモリ「表が多い記事は数値比較をメモ画像化」）

#### ④ 読者が記事で「体験」する

ここでの体験は、**読者が記事を読みながら自分の家・部屋に当てはめ、結果を自分ごととして感じること**を指す。筆者の体験談を作ることではない（筆者の体験は本人が記録したものだけ使う。ルート `CLAUDE.md` の規定どおり）。

記事には次のうち2つ以上を入れる。

| 体験の型 | 中身 | 例 |
|---|---|---|
| **当てはめ計算** | 読者の条件（広さ・枚数・予算）で結果が出る試算表 | 6畳の壁1面なら9m² → 遮音シート○枚・○kg・○円 |
| **判定フロー／チェックリスト** | 答えていくと「自分の場合」の結論に着く | 賃貸で壁に穴を開けられない → 選べるのは○○ |
| **今すぐできる確かめ方** | 道具を買う前に、家にあるもので確かめる手順 | 騒音計アプリで対策前後を同じ位置・時刻で測る |
| **前後の比較** | 対策前と後を数値と場面で並べる | 「○dB → ○dB。db-familiar-sound-scale の言い方で○○くらい」 |
| **次にやること1つ** | 記事の最後に、読者が今日できる行動を1つだけ | まず窓のすき間を測る |

### 4-5. slug・カテゴリ

- slug はメインKWの英訳（例: 遮音シート 効果 → `sound-insulation-sheet-effect`）。既存slugと語が重ならないか interlink-postlist で確認
- カテゴリは `bouon-category` で決める

## 8. 体験チェッカー（アウトライン段階でユーザーに聞く項目）

目的は2つ。①記事の言葉が、防音の専門家ではない読者に伝わるかを人間の目で確かめる。②筆者の体験と想像力を構成に取り込み、読者が記事の中で「自分の部屋なら」と体験できるようにする。

### 8-1. 書式

Claude は質問を `> [!question]`、ユーザーは直下に `> [!answer]` で答える。判断しやすいよう、Claude は**実際に記事で使う文言を引用して**聞き、なるべく選択肢（A/B/C）を付ける。

```markdown
## 体験チェック（YYYY-MM-DD）

> [!question] B1. 導入の1文目です。読んで場面が浮かびますか？
> 「夜11時、隣の部屋のテレビの声が、壁越しに言葉まで聞き取れる。」
> A. 浮かぶ　B. 浮かぶが自分の状況と違う（どこが？）　C. 浮かばない

> [!answer]
> B。うちは声より低音のドンドンが気になる。
```

- 体験の質問（C）の答えは、筆者の体験として記事に使ってよい（本人が記録したもの扱い）。Claude は答えにない体験・感想・数値を足さない。言い回しは控えめに保つ（「劇的に」などに盛らない）
- 体験以外の答え（A・B・D〜H）は調整の意見として使い、筆者の体験として書かない
- 答えを反映したら、アウトラインの「体験チェックの反映」節に「質問ID → 何をどう変えたか」を1行ずつ書く。質問と答えのブロックはアウトラインに残す（完成稿には載せない）

### 8-2. 質問の項目

`必須` は毎回聞く。ほかは記事の型と中身に合わせて選び、合計6〜10問にする。

| ID | 区分 | 質問の中身（Claude が具体的な文言・案を引用して聞く） | 使い道 | |
|---|---|---|---|---|
| A1 | 言葉 | タイトル案2つのうち、検索結果で開きたいのはどちらか。開きたくない理由は何か | タイトル確定 | 必須 |
| A2 | 言葉 | 見出し（H2）の並びだけを読んで、記事の流れと答えが分かるか。分からない見出しはどれか | 構成の修正 | 必須 |
| A3 | 言葉 | 専門用語（Dr値・面密度・透過損失など）と、その初出の説明文を見て分かるか。言い換えたほうがよい語はあるか | 用語の定義 | 用語が出る記事 |
| A4 | 言葉 | 引っかかる言い回し・「業者っぽい」「上から目線」に感じる文はあるか | さししの言葉の調整 | |
| B1 | 想像 | 導入や本文の場面描写を読んで、場面が浮かぶか。自分の状況と違う点はどこか | 場面の差し替え | 必須 |
| B2 | 想像 | 大きさ・重さの換算（畳・ペットボトルなど）は想像しやすいか。もっと身近な物はあるか | 換算の選び直し | 数値が多い記事 |
| B3 | 想像 | 音の通り道の説明（音源→壁→隣室）を読んで、どこで音が漏れるか思い描けるか | 仕組みの説明・図解の下書き | 知識系・効果確認型 |
| C1 | 体験 | この悩み（例: 隣の声で眠れない）を感じたことはあるか。いつ・どこで・どんな音だったか | 筆者の体験（導入・本音フック） | 必須 |
| C2 | 体験 | 記事で扱う物・方法を試した・調べた・見たことはあるか。そのとき何を感じたか | 筆者の体験（本文） | |
| C3 | 体験 | 試すのをためらった理由・買う前に迷ったことは何か | 本音と建前・FAQ | |
| D1 | 当てはめ | 試算の前提（例: 6畳・壁1面・賃貸）は、読者が自分に当てはめやすいか。別の前提がよいか | 当てはめ計算の条件 | 試算がある記事 |
| D2 | 当てはめ | 判定フロー・チェックリストの質問に、迷わず答えられるか。迷う質問はどれか | 分岐の言い方 | フローがある記事 |
| D3 | 当てはめ | 「今すぐできる確かめ方」を、家にある物で実際にできそうか | 確かめ方の現実性 | 手順型・効果確認型 |
| E1 | 数字 | 記事に出す数字の量は多すぎ・少なすぎではないか。意味が分からない数字はどれか | 数字の取捨・説明の追加 | |
| F1 | 図解 | 図解計画の説明（例: 壁の断面に遮音シートの位置を描く）を読んで、図が頭に浮かぶか。ほかに欲しい図はあるか | 図解計画の確定 | 図解がある記事 |
| G1 | 読後 | 読み終えたとき、次にやることが1つ浮かぶか。浮かぶ行動は記事の「次にやること」と同じか | 結びの行動 | 必須 |
| H1 | NG | 書いてほしくないこと、触れないでほしい話題はあるか | 範囲の除外 | |

### 8-3. 質問の作り方（Claude 向け）

- 1問に聞くことは1つ。「分かりやすいですか？」だけの抽象的な質問にしない。必ず記事で使う文言・案を引用する
- 選択肢で答えられる形を優先する。体験（C）だけは自由記述にする
- ユーザーの答えが短くても、推測で体験を膨らませない。足りなければ追加で1問だけ聞く
- 同じユーザーに同じ質問を何度もしないよう、過去のアウトラインの答え（例: 住まいの条件）は再利用し、「前回の答えを使います」と書く
