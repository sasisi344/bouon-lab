# /write-article — ボリューム指定ドラフト記事公開ワークフロー

**引数**: `{ボリューム} {ファイル名（省略可）}`

```
/write-article small 騒音トラブル対処チェックリスト.md
/write-article medium 在宅ワーカーの防音対策ガイド.md
/write-article high-quality 防音室ユニット完全比較2026.md
/write-article medium          ← _draft/ の記事ドラフトを一覧して選択
```

**ボリューム定義**:

| ボリューム     | 文字数目安     | 構成フレームワーク        | 主な用途                             |
| -------------- | -------------- | ------------------------- | ------------------------------------ |
| `small`        | 〜1,500字      | PREP（結論→理由→例→結論） | FAQ・チェックリスト・補助記事        |
| `medium`       | 2,000〜3,000字 | Problem-Solution          | 一般解説・比較・シナリオガイド       |
| `high-quality` | 5,000〜7,000字 | QUEST or PASONA（高密度） | ピラー・高単価商材・意思決定サポート |

---

## Step 0. 事前ロード（毎回必ず実行）

以下を読み込む。

1. `CLAUDE.md` — ライティング必須ルール・カテゴリ定義
2. `.agents/bouon-writer.md` — ペルソナ別トーン・マーケティングロジック
3. `.agents/persona/01_Consumer-Personas.md` — ターゲットペルソナ（A〜G）
4. `.agents/persona/00_Persona-Omega.md` — 編集長フィルター

---

## Step 1. 対象ファイルの確定

`$ARGUMENTS` の第2トークン以降をファイル名として扱う。省略された場合:

1. `_draft/` 内の `.md` ファイルをスキャンする
2. 以下をスキップしてリストから除外する:
   - `strategy-` / `cluster-ideas` / `owner-renovation-cluster` で始まるもの（企画ドキュメント）
   - `.py` / `.txt` などの非Markdownファイル
   - 本文が構想メモのみ（見出し・段落が存在しないもの）
3. 対象ファイルを番号付きで表示してユーザーに選択を促す

すでに `src/content/` に同一 slug が存在する場合はスキップしてユーザーに通知する（Globで確認）。

---

## Step 2. ドラフト読み込みとメタ情報抽出

ドラフトを読み込み、以下を判断する。

| 判断項目      | 確認方法                                                                                               |
| ------------- | ------------------------------------------------------------------------------------------------------ |
| **category**  | frontmatter の `category`。なければ本文から推定（knowledge / solutions / use-case / company / column） |
| **slug**      | frontmatter の `slug`。なければファイル名から生成（日本語はローマ字化・スペースはハイフン）            |
| **lang**      | frontmatter の `lang`。なければ `ja`                                                                   |
| **tags**      | frontmatter の `tags`。なければ本文から最大5個抽出                                                     |
| **persona**   | テーマからペルソナ（A〜G）と `.agents/bouon-writer.md` のセグメントを特定する                          |
| **framework** | 指定ボリュームから構成フレームワークを決定（下表）                                                     |

**フレームワーク決定表**:

| ボリューム     | メインロジック                                            | 副ロジック                                 |
| -------------- | --------------------------------------------------------- | ------------------------------------------ |
| `small`        | PREP                                                      | なし（簡潔優先）                           |
| `medium`       | Problem-Solution                                          | BEAF（Benefit-Evidence-Advantage-Feature） |
| `high-quality` | QUEST（防音室・ガジェット系）または PASONA（賃貸・DIY系） | 両方可                                     |

テーマが「賃貸・住居選び・DIY・オーナー投資」→ PASONA を優先。  
テーマが「配信者・楽器・プロ向け機器・スペック比較」→ QUEST を優先。

---

## Step 3. 本文の執筆

### 共通ルール（全ボリューム）

- 文体: **敬体（です・ます調）**、1文60文字以内
- 強調: `<strong>text</strong>` のみ。`**text**` は絶対禁止
- リストラベル: `- <strong>ラベル</strong> : 説明文`（コロン前後にスペース）
- H2/H3 に番号付け禁止（「1.」「2.」等）
- 内部リンク末尾スラッシュ必須: `[テキスト](/ja/collection/slug/)`
- MDXコンポーネントは import 文なしで使用可能
- 記事冒頭（frontmatter の直後）に必ず `<RegionBanner />` を置く
- テーブルのヘッダー行セルに `<strong>` を使わない（本文セルのみ使用）
- 数値推定値には「目安」「概算」を明記する
- 税務・法務・医療の内容には「専門家に確認を」の免責を入れる
- ドラフトの執筆用注記（「本番公開前に〜」等）は削除する

---

### small ── PREP 構成（〜1,500字）

**ベネフィット設計**: 読者が「1分で答えが分かる」体験を提供する。  
検索意図を満たす直接的な答えを最優先し、余分な文脈を削ぎ落とす。

```
[リード文] 結論を先出し（〜100字）

## {問い／課題を端的に示すH2}
  → Point: 結論を1〜2文で明示

## {理由・根拠 H2}
  → Reason: なぜそうなのかを物理法則・データで裏付け（〜300字）
  → Example: 具体例・数値・ユーザー事例（〜200字）

## {読者の次のアクション H2}
  → Point（再）: 結論の再確認＋行動を促す1文

[まとめ（CTA）]（〜150字）
```

- H2 は 2〜3 本
- 比較表・FAQ は原則なし（必要なら1つのみ）
- `<CtaBox />` を記事末尾に1つ配置する

---

### medium ── Problem-Solution 構成（2,000〜3,000字）

**ベネフィット設計**: 読者の「具体的な問題」を把握・整理し、実行可能な解決策を複数提示する。  
比較情報で「自分に合った選択肢」を選べるようにすることが価値の核心。

```
[リード文] 課題提示＋この記事で得られる答え（〜150字）

## {問題の背景・現状 H2}（〜300字）
  → 読者が抱える具体的な悩みを共感的に描写
  → 数値・事例で問題の深刻さを示す

## {解決策の全体像 H2}（〜300字）
  → 解決の方向性を3〜4点で整理（箇条書きで概観）

## {解決策A H2}（〜400字）
  → BEAF: Benefit→Evidence→Advantage→Feature の順で展開

## {解決策B H2}（〜400字）
  → 同上

## {選択肢の比較 H2}（〜400字）
  → 比較表を1つ配置（自分の状況から選べるよう設計）

## まとめ（〜200字）
  → 行動への橋渡し＋関連内部リンク2〜3本

[CTA: <CtaBox />]
```

- H2 は 4〜5 本（H3 は必要なもののみ）
- 比較表は1つ
- `<AffiliateCard />` は商品推薦が適切なセクションに1〜2個配置可

---

### high-quality ── QUEST または PASONA 構成（5,000〜7,000字）

**ベネフィット設計**: 読者が「意思決定の全プロセス」を完結できる権威性の高い記事。  
「なぜ今これが必要か → 何を選ぶか → どう動くか」までを網羅し、外部検索不要の状態を目指す。

#### QUEST 構成（配信者・楽器・機器・スペック比較向け）

```
[リード文] 課題提示＋記事のゴール（〜200字）

## Qualify: あなたに必要な情報はここにあります（〜300字）
  → 対象読者を絞り込み「この記事があなたのためにある」を明示

## Understand: 問題の本質を理解する（〜600字）
  → 技術的背景（dB・Hz・遮音等級等）を専門的に解説
  → ユーザーがよく誤解するポイントを2〜3点挙げる

## Educate: 解決策の全知識を習得する（〜1,500字）
  → メイン解決策を詳細に解説（H3で細分化）
  → 複数の選択肢を比較表で整理（2〜3表）
  → 具体的なスペック・数値・費用感を提示

## Stimulate: 今行動する理由（〜600字）
  → 行動しない場合のリスク・機会損失を具体的に示す
  → 成功事例・導入メリットの数値（ROI等）

## Transition: 次のステップへ（〜400字）
  → 具体的な行動手順（3〜5ステップ）
  → 関連記事・サービスへの内部導線

## よくある質問（FAQ）（〜600字）
  → 3〜5つのQ&A

## まとめ（〜300字）
  → 記事全体の要約＋行動喚起

[CTA: <CtaBox /> + <AffiliateCard />]
```

#### PASONA 構成（賃貸・DIY・オーナー投資向け）

```
[リード文] 痛みを直撃する問題提起（〜200字）

## Problem: あなたが直面している問題（〜400字）
  → 読者の現状を具体的に描写（騒音・空室・コスト等）
  → 問題を放置した場合の損失を数値で示す

## Agitation: 問題はさらに深刻化する（〜400字）
  → 悪化シナリオを段階的に示す
  → 競合他社・周辺物件との差が広がることを示唆

## Solution: 解決策の全体像（〜400字）
  → この記事が提示する解決策の方向性を概観
  → 「なぜこの方法が有効か」を物理的根拠で裏付ける

## Offer: 具体的な実行プラン（〜1,500字）
  → 費用・手順・期間を細分化して解説（H3で段階分け）
  → 比較表・チェックリストで選択肢を整理

## Narrow: あなたのケースに当てはめる（〜600字）
  → タイプ別（予算帯・物件種別・目的等）の推奨案
  → よくある失敗パターンと回避策

## Action: 今すぐできる第一歩（〜400字）
  → 具体的な行動を3〜5ステップで提示
  → 関連記事・サービスへの内部導線

## よくある質問（FAQ）（〜500字）
  → 3〜5つのQ&A（Persona Ω フィルターで誇大表現をチェック）

## まとめ（〜300字）
  → 行動喚起＋免責（必要な場合）

[CTA: <CtaBox /> + <AffiliateCard />]
```

**high-quality 共通注意点**:

- H2 は 6〜8 本、H3 は各H2に1〜3本
- 比較表は2〜3個
- `<AssetValueTable />` は投資・費用比較が含まれる場合に使用可
- `<SmartLink href="..." />` で関連記事への内部リンクを3〜5本配置
- Persona Ω チェック必須: 「遮断」→「低減」、「完全防音」→「高い遮音性能」等

## Step 4. frontmatter 生成

```yaml
---
title: "主要KWを左側に | 35-42文字"
description: "SEO用サマリー | 80-120文字"
slug: "unique-slug"
date: "YYYY-MM-DD"
lastmod: "YYYY-MM-DD"
draft: false
lang: "ja"
category: "{collection名と一致}"
tags: ["タグ1", "タグ2"]
image: ./cover.png
---
```

- `date`: ドラフトの `date` を使用。なければ本日の日付
- `lastmod`: 本日の日付（2026-04-14）
- `draft: false`（本番公開）
- `volume` / `voice` 等の非標準フィールドは含めない
- `image: ./cover.png` はクォートなし・エスケープなし

---

## Step 5. カバー画像の生成

記事の `description` と主要テーマから英語プロンプトを生成し、スクリプトを実行する。

```bash
node .agents/scripts/generate-image.js --preset cover "英語プロンプト" "src/content/{category}/{lang}/{slug}/cover.png"
```

**プロンプト生成ルール**:

- **英語**で書く（生成精度向上のため）
- 記事のメインビジュアルを具体的に描写する
- 人物の顔・テキストオーバーレイ・著作権物は避ける
- BouonLab スタイル: Modern, Calm, Professional（防音・静寂・スタジオ系ビジュアル）
- 例: `"Soundproof booth setup in a modern home studio, acoustic panels on walls, soft warm lighting, no people, professional photography style"`

スクリプトが失敗した場合（APIキーなし等）: `image: ./cover.png` を frontmatter に残したまま、ユーザーに通知して続行する。

---

## Step 6. ページバンドルの作成

以下のパスに `index.mdx` を作成する。

```
src/content/{category}/{lang}/{slug}/index.mdx
```

ファイルの順序:

```mdx
---
{ frontmatter }
---

<RegionBanner />

{本文}
```

## Step 7. ドラフトファイルの削除

```bash
rm "_draft/{元ファイル名}"
```

```

  node .agents/scripts/generate-image.js --preset cover "..." "src/content/{category}/ja/{slug}/cover.png"
```

## カテゴリ判定基準

| category    | 読者・内容                               |
| ----------- | ---------------------------------------- |
| `knowledge` | 一般ユーザー向け解説・Myth Buster系      |
| `solutions` | オーナー・プロ・購入検討者向け意思決定   |
| `use-case`  | 配信者・在宅ワーカー等の特定ペルソナ向け |
| `company`   | メーカー・サービス・B2B分析              |
| `column`    | 広い読者層向けコラム                     |

---

## 制約事項

- 画像生成はこのコマンド実行時のみ行う
- ドラフトの slug・URLは変更しない（既存SEO評価を保護）
- `pnpm build` は実行しない（ユーザーが手動で確認）
- `git commit` は実行しない（ユーザーが手動でコミット）
